# Rigid bodies: cut-free rock falls as one piece

Research only; nothing built. Read: CLAUDE.md invariants, grid.rs (chunks, `touch`, `awake`/`active`), entities.rs (Bag/Projectile are plain fixed-size hashed structs), enemies-design.md section 3 (proximity stepping rule, which I reuse rather than repeat).

## 1. Detection
Trigger: any tick where a solid cell was removed (dig, explosion, acid, lava). Collect the removed cells' solid neighbours as seeds (cap: 64 seeds per tick, the rest carried to the next tick in a fixed-order queue, which is state and must be hashed/snapshotted, or else dropped deterministically).
For each seed run a bounded flood fill over *structural* solids (Rock, Bedrock, plus whichever "static" materials count). Two outcomes:
- reaches Bedrock or any cell flagged anchored, or exceeds the cap `N_MAX` cells: anchored, stop (early exit is the common case, usually after a few hundred cells at most, but a cut near the surface can walk a long way before it hits anything anchored).
- fill ends with fewer than `N_MAX` cells and no anchor: a free island.
The flood is a pure function of the grid, so every client computes the same answer. Worst case per seed is `N_MAX` cell visits; with 64 seeds and `N_MAX` = 512 that is about 33k visits/tick, comparable to one awake chunk row. Use a visited stamp array (u32 tick stamp, scratch, not hashed) so no clearing cost. Problem to solve: "anchored" needs a definition. Bedrock only is too strict (the world is mostly rock hanging off other rock far away; a bounded fill would call everything free). Practical definition: a fill that exceeds `N_MAX` is treated as anchored. That means large cut-free masses never fall (see section 5), which is the v1 compromise.
Also needs the frozen-chunk rule: the fill must not read cells in non-`active` chunks (they are frozen and the result would depend on player positions through stale cells; actually it would still be deterministic, but the island could straddle frozen space). Simplest: a fill that touches a non-active chunk counts as anchored.

## 2. Representation
Two options.
A. **Lift and rasterise on rest (recommended).** Remove the island's cells from the grid, store them in a `Body` entity: `{cells: Vec<(i8 dx, i8 dy, u8 mat, u8 aux)>, x, y (fixed-point), vx, vy}` plus, later, `angle, omega`. Hashed and snapshotted like Bag. While in flight, nothing in the grid represents it, so liquids/sand flow into the vacated space. On landing, write cells back (displace or burn whatever is in the way: see below).
B. **Always rasterised (Noita-style).** Body cells are written into the grid each tick and erased the next. Gives free interaction with fluids (water pushes, sand lands on it) but doubles the grid writes, makes the grid contain transient cells that must be undone in the right order, and breaks "Rock is static" assumptions everywhere (digging a moving body's cell, acid eating it). Order dependence with the cell pass is large. Reject.
Option A cost: a body is a new entity kind; the snapshot gains a variable-length section (cells), `MAX_BODIES * N_MAX * 4` bytes worst case (e.g. 16 * 512 * 4 = 32 KB, acceptable but it changes snapshot format; the game is not live so a format break is fine).

## 3. Simulation in integers
Rotation: `trig.rs` has `dir(angle) -> (i32,i32)` (fixed-point unit vectors), so rotating a cell offset is two integer multiplies per cell. Collision of a rotated cell set against the grid: rotate every cell (<= N_MAX), round to grid, test for solid. Resolution needs contact points, a normal, an inertia tensor (sum of r^2 over cells, integer fine), and impulse maths with divisions. All doable in i32/i64, but the hard part is not arithmetic: it is stability. Rasterised rotated sprites leave gaps and overlaps, resting contact jitters, and tuning stacking/friction without a reference engine takes days. Expect a rotating body to creep, vibrate or tunnel without careful sub-stepping. I would not do this in the time left.
**Scoped v1: translation only.** State `x, y, vx, vy` (fixed-point, like projectiles). Each tick: `vy += g` (clamped), move one axis at a time in sub-steps of at most 1 cell (`MAX_SUBSTEPS` style DDA, see tuning.rs:46), test the body's cells against the grid with a bounded test (<= N_MAX reads per sub-step; use a precomputed bottom-edge or leading-edge list to cut it to roughly the body's width). Blocked below: settle. Blocked sideways: zero vx. Settling = write cells back. No inertia, no angle, no impulse maths, no body-body contact beyond "stop at overlap". This is perhaps a tenth of the rotating version: roughly 300-400 lines of Rust against 1500+, and nothing in it is hard to make deterministic. Visual cost: it looks like a falling slab, not a tumbling boulder.

## 4. Multiplayer and determinism difficulties
- **Floats banned:** solved by fixed-point; rotation is the only place it bites (section 3). Avoid division and use shifts. No marching squares or triangulation is needed because bodies are cell lists, not polygons; that is the big simplification over Noita.
- **Order dependence between bodies:** bodies step in id (spawn) order, each reading the grid as left by the previous one. Deterministic, but two bodies touching resolve asymmetrically (id 0 wins). In v1, treat other bodies as non-solid or as "settle if overlapping a body already at rest", never mutual impulses. A body landing on a body that has already rasterised just sees ordinary solid cells, which is the clean case.
- **Sleeping and frozen chunks:** use the enemies-design section 3 rule: a body steps only if inside a rectangle strictly within the `active` rect around an active player, otherwise it is frozen by rule (no movement, no timers). It must never read `awake`. Its writes (lift and landing) go through `Grid::set` so `touch` wakes neighbours, as `Dig` does. Edge case: a body falling out of the stepped rect mid-air freezes in the air; acceptable (it resumes when a player returns). Add a D7 scenario with a body in flight.
- **Snapshot and late join:** bodies are hashed state; a late joiner receives the snapshot with the body list (section 2). Nothing is derived from scratch, so no problem, but snapshot size grows (cap it, section 5). The lift writes to the grid and entity list in the same tick on every client, so there is no window where clients disagree about whether the island exists.
- **Per-tick cost:** every client steps every in-range body. Bounded by `MAX_BODIES_STEPPED` (e.g. 8) x `N_MAX` x substeps (<= 8) = about 32k cell reads worst case. Same order as the flood fill.
- **Landing on a player:** player positions are client-predicted (the sim only sees `Pos` inputs, enemies-design section 2 covers this). Do not make a body collide with players physically; players are not in the grid. Damage on landing is a pure function of sim state: if a settling body's cells overlap a player's box, apply damage (HP loss per overlapping tick, or crush: the same code path as acid/lava damage to the avatar). Warn: because the player's position is client-supplied, the player can step out of the way after the sim has decided, which is fine, since the sim decides on the position it holds. The ugly cases are a player standing where the body lands (cells written back over the player: the avatar ends up inside rock; push the player out or let the existing "stuck in rock" handling deal with it, which needs checking) and a player riding or digging under a falling body. Recommend: body does not move into a cell overlapping an alive player's box (it stops and waits one tick); damage only from the fall speed at first contact with a player box. Simplest honest rule: no body damage in v1, bodies stop above players.
- **Huge bodies:** past `N_MAX` the fill reports "anchored" and nothing happens (section 5).
- **Landing writes:** on settle, cells go back to empty cells only; cells that would land on liquid/gas/sand displace it upward or are swapped (decide: displaced fluid is destroyed, bounded, deterministic). Cells that cannot be placed turn to Rubble/Sand.
- **Cheating:** a hostile client can trigger many cuts only through the inputs that already exist (Dig, Paint, spells), all already clamped; the queue and caps bound the cost.

## 5. Bounded work
Constants: `N_MAX` = 256-512 cells per body; `MAX_BODIES` = 16 stored (decode refuses more, like `MAX_PROJECTILES`); `MAX_SEEDS_PER_TICK` = 64; per-tick flood budget (total cells visited) = 16k, leftover seeds roll to the next tick. Past the caps: an oversized island stays in place (cheapest, but players will see a hanging ceiling, which matches the current game), or it converts to Rubble/Sand at the cut, in place or as falling powder (reuses existing grid physics, bounded because the grid already bounds it). A body count over `MAX_BODIES` also crumbles to Sand rather than being dropped silently. The flood cost is paid only on ticks with a removal, and repeated digging near a wall pays it every tick (worst case 16k visits/tick, comparable to existing cell passes). Sort seeds into a fixed order (by y then x) so the result is independent of the order inputs applied.

## 6. A cheaper alternative
**In-grid shift (no new entity):** when the flood finds an island <= N cells, move it down one row per tick in place (read cells, clear them, write them one row lower, bottom row first, if every cell below the island's bottom edge is Empty/fluid). State lives only in the grid, so snapshot, hashing, late join and sleeping stay unchanged, except that `touch` must wake the chunks it crosses; the island needs a "falling" mark, otherwise it must be re-found each tick (re-run the fill each tick for the touched region: cost is the same bounded fill). It is just "Sand for chunks": falls straight, lands, stays. Maybe 100-150 lines in grid.rs. Gotchas: it needs a flag so a resting island is not re-scanned forever (an `aux` bit or a per-chunk dirty list), and a liquid in the way (stop, or displace upward).
**Crumble:** islands under N cells convert to a new falling powder ("Rubble"); trivial (about 40 lines plus a material), and the grid already handles the physics. Loses the "solid piece" look but gives the Noita-ish "the ceiling collapses" feel.
Effort vs payoff: crumble gives about 60% of the visible effect for about 10% of the effort; in-grid shift gives about 80% for about 25%; translation-only bodies about 85% for about 50%; tumbling gives the full effect for 100%+ with large unknowns.
